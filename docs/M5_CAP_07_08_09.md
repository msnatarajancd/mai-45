# CAP-07/08/09 Recovery acceptance

## Scope and existing gaps

The integrated app.py Recovery page reuses the existing deterministic planner, repository,
M1 extraction consumer, official directory, damage records and insurance summary. No model
client, agent or external submission was added. M1 only proposes facts; confirmation remains
mandatory. This change makes the existing plan household-specific, adds missing status-event
history, and persists reviewed applicability instead of only appending tasks.

## CAP-07 - Personal plan

`create_demo_draft_plan(case, records=None)` accepts existing confirmed models. Typical
flood/outage/accommodation/damage cases produce 4-7 prioritized tasks; sparse reports are
not padded with invented needs. Rules consider accommodation, reported utilities, housing,
damage items, explicit transportation/supply needs and insurance preparation. Unknowns do
not become outages or inferred household members/services. Every task explains its purpose;
relevant tasks include prerequisites. Damage documentation is conditional on safety and
never authorizes building entry or handling hazards.

Task resource_categories reference the existing official directory. The UI renders official
organizations, URLs, geographic scope, verification dates and limitations via find_resources,
using confirmed county only. These pathways are not M3-reviewed task instructions or live
availability/eligibility checks. No provider, shelter opening, insurance coverage or outcome
is inferred. Source_reference retains its prior reviewed-guidance meaning.

Drafts retain their original case and records version. Generating/displaying them writes
no plan/tasks. UI approval inserts and activates a new plan in one transaction via the
existing approve_plan method's optional new_draft/explicitly_approved arguments. A stale
assessment/record version, existing active plan, duplicate ID or failed write rolls back
that operation. Existing callers and old JSON remain compatible.

## CAP-08 - Progress and history

All four existing statuses remain supported: Not started, In progress, Completed and Blocked.
Status updates still require an active approved plan, persisted no-danger assessment and
expected progress version in the UI. An additive recovery_task_events table records actual
user transitions with case/plan/task IDs, prior/new statuses and UTC timestamp, in the SAME
transaction as the plan write. list_task_history(case_id) reads them across revisions.
No legacy events are fabricated. Prior historical plans remain available.

Current outstanding/blocked counts and the progress bar exclude tasks explicitly accepted
as no longer applicable. Their historical status is retained and visible. They are not
silently marked Completed. The UI and downloads use reviewed descriptions/applicability;
original task objects preserve prior text and statuses for history.

## CAP-09 - Review and reconcile

Preview still performs no writes and retains all prior task IDs/statuses. Additive TaskReview
metadata holds accepted current applicability, explanation, description and priority. Initial
tasks remain historical objects; consumers should use task_reviews for their current view.
The integrated Recovery UI sorts current tasks by effective priority. Assistant plan
displays and the standalone dashboard distinguish no-longer-applicable history from
current tasks and use the accepted descriptions/priorities.

Confirmed accommodation changes to arranged/not-needed remove Temporary housing from current
needs in the reviewed intake; the proposed change is shown BEFORE approval. Reported electricity
restoration changes only relevant follow-ups and never establishes safety. Other unknown or
unavailable utilities remain explicit. Completed work is preserved. A genuinely recurring
need after a completed equivalent gets a new follow-up, not a status reset. Additions are
not duplicated while an outstanding equivalent exists.

Previews can include original/updated RecoveryRecords snapshots. Newly confirmed damaged items
receive separate documentation follow-ups, without deleting prior damage or reopening earlier
completed documentation. Confirmed item IDs are tracked in the accepted plan so later previews
do not repeatedly add the same follow-up. Conversational damage IDs are stable per review
so its preview and explicit acceptance refer to identical records.

The approval transaction revalidates case, active plan/progress, records snapshot/version,
matching confirmed records, all deterministic recommendations and applicability metadata.
Forged metadata and stale proposals fail closed. The accepted assessment, records, plan and
reassessment history commit together. Status-event history stays intact. Pending and persisted
danger protections remain authoritative; ordinary changes cannot clear danger.

## Acceptance example

Confirmed flood + electricity outage + needed accommodation + furniture damage produces:

1. HIGH: Review temporary housing options (official housing information; no availability claim).
2. HIGH: Record utility availability and gaps (confirm provider; no repairs).
3. HIGH: Review safe recovery boundaries (emergency/reentry limits).
4. MEDIUM: Organize known damage information (furniture; safe known information only).
5. LOW: Prepare an insurance discussion draft (confirmed damage; no coverage/submission claim).
6. LOW: Review saved recovery records and follow-ups (official disaster-assistance pathway).

After user-confirmed temporary lodging and restored electricity, housing/outage work is no
longer current, but any Blocked/In progress/Completed status and history remain unchanged.
Unrelated tasks continue. A new refrigerator documentation task is proposed. Nothing changes
until approval; the accepted insurance summary contains both furniture and refrigerator.
